# Lesson Format

How a Track and its Lessons are laid out on disk. Vocabulary follows [CONTEXT.md](../CONTEXT.md). Everything here is checked when the site builds: a mistake fails the build with a file and a reason, never a broken page.

```
lessons/
└── memory/                       ← a Track; its directory name is the Track id
    ├── track.yaml
    └── method-calls/             ← a Lesson; its id is "memory/method-calls"
        ├── lesson.yaml
        ├── narration.md
        ├── Program.java          ← the Lesson Program (Execution Lessons only)
        ├── *.java                ← any other classes it uses
        ├── variants/
        │   └── <variant-id>/     ← only the files this Variant changes
        └── traces/               ← generated by `npm run record`; git-ignored
```

## track.yaml

```yaml
title: Memory
order: 3            # position among Tracks; must be unique
description: One or two sentences shown on the home page and the Track page.
```

## lesson.yaml

```yaml
title: Method calls and Frames
kind: execution     # execution | timeline | pipeline
visual: how-java-runs  # Pipeline Lessons only: which bespoke visual draws it
order: 1            # suggested position within the Track; must be unique in the Track
summary: One sentence shown in Track listings.
prerequisites:      # Lesson ids; advisory links, never locks. Unknown ids and cycles fail the build.
  - memory/objects-and-references
detail: simple      # default Detail Level: simple | jvm
variants:           # optional; defaults to a single "default" Variant
  - id: default     # must come first
    label: As written
  - id: synchronized
    label: With synchronized
    schedule: contended   # optional: record under schedules/contended.yaml
```

## timeline.yaml

Timeline Lessons (`kind: timeline`) have a `timeline.yaml` instead of a Lesson Program. Each Version Stop is one Step, and its `id` doubles as the Marker that `narration.md` anchors to:

```yaml
stops:
  - id: java-5                  # unique; narration uses ## @java-5
    version: J2SE 5.0           # as Java named it at the time
    released: "2004-09-30"      # quoted YYYY-MM-DD; stops must be in date order
    kind: release               # release (default) | event, shown as a Turning Point
    landmark: true              # bigger dot and card
    lts: false                  # long-term support badge
    headline: The biggest change to the language since 1.0
    features:                   # `backticks` mark code
      - Generics, so collections know what they hold
    code:                       # optional before/after comparison
      before: { label: Java 1.4, source: "..." }
      after: { label: Java 5, source: "..." }
    lesson: history/java-5-varargs   # optional link to an Execution Lesson that shows the change running
```

The stop holds the facts (what changed). `narration.md` holds the story (why it mattered) and the Predict Prompts. Timeline Lessons have one Variant and no JVM Detail Level, so their narration headings take neither suffix.

## Pipeline Lessons

A Pipeline Lesson (`kind: pipeline`) animates a flow of Stages with its own bespoke visual. Each one looks different, so there's no generic data format. Its Steps and drawing code live in `site/src/renderers/pipeline/<visual>/`, registered by name in `steps.ts` and `renderers.ts`, and `lesson.yaml` picks one with `visual:`. Step ids are the Markers `narration.md` anchors to.

If the lesson directory has a `Program.java`, `npm run record` writes its real `javap -c -p` listing to `traces/bytecode.txt`, so any bytecode the visual shows is exactly what `javac` produced.

## Variants

A Variant is the Lesson's root `.java` files with same-named files from `variants/<id>/` replacing them (files that exist only in the Variant's directory are added). Put only the changed files in the Variant's directory. The `default` Variant is the root files as they are. A Variant may instead, or also, name a Schedule, so "the same code under different timing" is a Variant too.

## Schedules

A Lesson Program that starts threads runs them one at a time, in a deterministic order. Without a Schedule each thread runs until it finishes, blocks or waits, in the order the threads started. A Schedule in `schedules/<id>.yaml` picks the interleaving instead, as a list of turns:

```yaml
- run: main
  until: join          # a Marker: stop when main is about to run that line
- run: A
  until: increment
  steps: 1             # ...then this many more of A's Steps (e.g. one Sub-step: the read)
- run: B
  until: blocked       # or `waiting`: B's turn ends when it can't continue
- run: A               # no `until`: run A until it finishes
```

`run` names a thread by its Java name (`new Thread(task, "A")`). After the last turn, any threads still unfinished run one at a time in start order. A Schedule that names a thread that hasn't started, expects a Marker a thread never reaches, or leaves turns unused fails the recording and names the turn. If every remaining thread is blocked on another's lock, the recording ends in a deadlock, which is a valid ending for a lesson about deadlocks.

Use `synchronized` blocks rather than `synchronized` methods in Lesson Programs, so a blocked thread is shown at a line of your code. `ReentrantLock` works too, and is shown like a `synchronized` lock. Virtual threads (`Thread.ofVirtual().name("A").start(task)`) work like platform threads in Schedules, and show whether they're on a carrier. Keep a lesson under 8 virtual threads, the number of carrier threads lessons run with. A thread calling `wait()` gets its own Step (shown as waiting), and its turn can end with `until: waiting`.

Variants often take different paths through shared files: a thread that never has to wait, a program that deadlocks. A Marker only has to be reached by one Variant, and narration anchored to it must then be scoped (`in <variant>`) to the Variants that reach it. The build tells you which anchor doesn't resolve where.

## Sub-steps

Add `// @substeps` to a line to record it one meaningful instruction at a time (see [trace-format.md](trace-format.md#sub-steps)). Put it on lines where a race happens *inside* the line, like `count++`, and nowhere else: it makes a lesson longer. It can share the comment with a Marker: `count++; // @mark increment @substeps`.

Give every Variant the same Markers wherever the moment is the same. Switching Variant during playback jumps to the latest Marker passed, so shared Markers are what let the Learner compare "the same moment" across Variants.

## Markers

A Marker is a `// @mark name` comment at the end of a line of the Lesson Program. Names are `lowercase-with-dashes`, and the Player strips them from the code it shows. See [trace-format.md](trace-format.md#markers) for how they resolve to Steps, including the `name@thread#hit` form for lines that run more than once.

## narration.md

The Lesson's only explanatory text. Each `##` heading anchors a block to a Marker (or `@start` for the first Step):

```md
## @start

Shown from the first Step until the next anchor. Wrapped lines join into one paragraph, a blank line
starts a new one, and `backticks` mark code.

## @start jvm

Replaces the block above when the Learner has JVM detail on. `simple` works the same way.

## @call-add

Shown from the call-add Marker's Step onwards.

## @use-box in mutate

Only in the `mutate` Variant. `in <variant>` combines with a Detail Level (`## @start jvm in mutate`).
When several blocks share an anchor, the most specific one wins: Variant, then Detail Level, then generic.

## Predict @call-add

What happens on the Stack when `add(x, y)` is called?

- [ ] One wrong answer
- [x] The right answer (exactly one)
- [ ] Another wrong answer

> The explanation shown after the Learner answers.
```

`## Predict @marker in <variant>` limits a prompt to one Variant and replaces a generic prompt at the same Marker.

A Predict Prompt pauses playback at its Marker's Step. The Learner has to answer before stepping past it, then sees the explanation and what actually happens. Every anchor must match a Marker in every Variant's Trace.

## Recording

```bash
npm run record    # records every Variant of every Execution Lesson into its traces/ directory
```

`npm run build` records first, and CI does the same on every push. Traces are never committed.
